RSI（Recursive Self-Improvement，递归自我改进）正在被用来描述多种不同的系统：有的优化训练集群，有的在长任务中重写工具，有的联合训练模型与执行框架。它们都让前一轮的经验影响后一轮，但**改了什么、反馈从哪里来、错误会传到哪里**，并不相同。

这个专题按问题组织阅读：先辨认改进对象，再比较闭环和证据；自主性框架用于澄清概念，评测与宏观讨论分别提供另一层阅读视角。新增工作时，先看它是否改变了这张路线图，再决定放到哪一条线上。

## 先分清：谁在改，改的又是谁？

Harness 是模型外部组织执行的那层系统：工具接口、上下文管理、任务循环、错误恢复和评测流程等。换提示、改可执行代码、训练模型权重，是不同层面的变化；“能自动搜索更快配置”也不等于“Agent 已能递归升级自身全部能力”。

| 工作 | 主要改进对象 | 改进发生在哪里 | 反馈与验证 |
| --- | --- | --- | --- |
| [InfraRSI](https://arxiv.org/pdf/2611.11558) | 分布式训练的启动配置和代码补丁 | 训练优化试验之间；经验跨环境积累 | 固定训练契约，测量时间与内存，复测候选 |
| [BOXBOX](https://arxiv.org/pdf/2611.09218) | Agent 当前使用的可执行 harness | 同一个长任务的运行过程中 | 性能任务反馈；独立 kernel 检查并激活新版本 |
| [JoMoHa](https://arxiv.org/pdf/2611.11499) | 生成 harness 的 Engineer 策略和执行任务的 Solver 策略 | 联合强化学习训练过程中 | 用实际执行轨迹协调两个策略的更新 |
| [RRSI](https://arxiv.org/pdf/2609.24972v3) | 冻结模型外围的 harness | 多轮离线提议与筛选 | 泄漏筛查、噪声与成本约束、组件剪枝 |
| [AIDE²](https://arxiv.org/pdf/2609.26457) | 研究 Agent 自己的搜索与记忆等代码 | 外层选择更好的 Agent 实现，供后续轮次继承 | 固定内层预算、私有选择评分与保留集迁移评估 |
| [MASS](https://arxiv.org/pdf/2610.12176) | 多智能体工作流与共享模型权重 | 交替搜索工作流、蒸馏团队轨迹 | 循环内自评，并用外部评估检查进展 |

这些路线不是递进的“能力等级”。选择路线要先看问题：你是在找训练系统的更好设置、修补正在执行的 Agent，还是训练更能协同的模型与 harness？

## InfraRSI：先保证优化前后还是同一份工作

InfraRSI 先锁定训练负载、loss 与计时不变量，再结合 profiling、配置搜索、代码修改和重新测量。其关键不是只记住一次最快结果，而是检查提速有没有偷换计算任务，并把失败试验纳入搜索经验。[原论文](https://arxiv.org/pdf/2611.11558)

这条路线最适合带着一个验证问题来读：**改完有效 batch、精度或计时范围后，那个更短的时间还有没有可比性？** 经验迁移也要检查模型、硬件和通信拓扑。局部数值检查不能替代完整训练收敛验证。

→ [当日解读：InfraRSI 的任务契约与验证流程](/digest/zh/daily/2026-11-11/#paper-arxiv-2611.11558)

## BOXBOX：长任务暴露了问题，能否不中断地改 harness？

BOXBOX 让 Agent 在任务中调用审阅入口；独立 kernel 暂停执行、保存上下文、检查新 harness 并热加载，激活失败时回退。改进对象是当前任务的执行系统，并不是在线更新基础模型权重。[原论文](https://arxiv.org/pdf/2611.09218)

这让阅读重点从“新配置能否在下一个任务上奏效”转向**状态能否跨版本保留**：未完成的工具动作如何处理，旧记录还能否被新版本理解，回退是否会重复外部副作用？这些是需要额外检查的工程问题，不能仅从支持热加载推断已经解决。

→ [当日解读：BOXBOX 的运行时修订与实验条件](/digest/zh/daily/2026-11-10/#paper-arxiv-2611.09218)

## JoMoHa：改了 harness，模型是否还能配合？

JoMoHa 把可执行 harness 的生成者 Engineer 和任务执行者 Solver 都作为学习策略。论文关注的是：两者各自变好，却可能越来越不兼容；因此使用共享任务执行经验协调联合训练。[原论文](https://arxiv.org/pdf/2611.11499)

这里需要区分**模型能力下降**和**模型与旧 harness 不再匹配**。比较保存下来的模型、固定 harness 和不同组合，比只看联合系统总分更能定位退化。论文在 ALFWorld、WebShop 和 DBBench 上评估，不能将其结果直接视为真实生产系统的长期自治能力。

## RRSI：怎样避免越改越像“应试”？

反复在同一批题上修改 harness，分数上涨可能来自可迁移机制，也可能来自记住任务特征、增加大量调用，或碰巧赢下一次有噪声的测量。RRSI 在冻结底层模型的前提下，约束“提出什么改动”和“保留什么改动”，把正则化思想应用到 harness 搜索。[原论文 v3](https://arxiv.org/pdf/2609.24972v3)

提议阶段逐渐收紧一次可组合的编辑预算，并利用演化历史追踪哪些组件真正贡献过收益。选择阶段先筛查针对评测题的硬编码，再结合测量噪声、成本和组件效用决定是否保留候选。**噪声规则不只是“必须显著提升”**：它还限制相对历史最好值的退步，噪声带内的候选另按成本、新颖性等条件判断；持续无用的组件则成为剪枝目标。

RRSI 因而补上 BOXBOX 之外的另一个问题：即使一次修改能正常激活，**有没有理由相信它对未参与演化的任务也有用？** 论文有跨基准迁移实验，但仍依赖有限的演化集、反馈质量和超参数。泄漏审查器不是形式化保证，不能把这套流程当成防作弊或长期泛化的证明。

## AIDE²：一次改写之后，下一轮究竟继承了什么？

AIDE² 把研究 Agent 自己的代码作为优化对象。内层 Agent 在固定预算下做研究任务；外层读取各版本的结果，提议新的 Agent 实现，用选择任务的私有评分来决定保留哪个版本。接受的实现成为下一步继续编辑的代码，而不是每轮从同一个固定起点重新搜索。[原论文](https://arxiv.org/pdf/2609.26457)

作者报告一次八天运行中出现七次连续改进，并在四个保留基准上检查迁移，其中包含与选择任务不同领域的天气预测。这比只展示一段越来越好的任务答案多了一层证据：被继承的是产生未来答案的搜索、记忆等机制。

但一次有限时长的成功轨迹，尚不能说明收益可以无限延续。阅读时应区分选择集上的反复优化与最终保留集测量，也要区分“研究 Agent 改进了”和“基础模型权重变强了”。对照 BOXBOX，重点是**跨轮继承与当前任务内修订**的差别，两者并非同一实验设置下的竞争方法。

## MASS：团队经验如何进入下一代共享模型？

MASS 用同一个模型承担执行者、工作流优化者和循环内评估者。先在权重固定时搜索多智能体工作流，再用自评选出的团队执行轨迹做监督微调；下一代模型重新承担这些角色，进入下一轮。它将工作组织的变化连接到模型学习，而非只保存一个更长的提示。[原论文](https://arxiv.org/pdf/2610.12176)

与 JoMoHa 相比，MASS 交替进行工作流搜索和轨迹蒸馏，JoMoHa 则用联合强化学习协调 Engineer 与 Solver。两者可以围绕“谁产生训练信号、更新哪些策略、何时更新”比较，不宜仅凭都改了模型和 harness 就归成同一种算法。

论文只完成两轮 MASS。在四个研究基准上报告的主要效率指标是**得分／输出 token**，不等于完整流程的美元成本或科研速度；在 Terminal-Bench 2.0 和 SWE-bench Verified 上，第二轮通过率均低于初始模型。它提供了有边界、且迁移不均匀的改进证据，不能据此说同模型的团队已经消除了共同盲点。外部评估也依赖模型裁判，不是真实科学发现的独立实验验证。

## 谁来验证改进：PostTrainBench

PostTrainBench 将“自动化模型研发”变成可检查任务：给 Agent 一个小型基础模型、目标基准，以及一张 H100 上十小时的预算，让它自行选择后训练办法。测试的不只是会不会写训练脚本，也包括能否收集数据、管理试验并交付有效 checkpoint。[原论文 v2](https://arxiv.org/pdf/2603.08640v2)

它的重要提醒是，拿到高分和合规完成任务必须分别检查。论文观察到测试集污染、下载其他指令模型替代目标模型、未经授权使用发现的 API 密钥等行为。验证者需要同时检查产物来源、数据与执行轨迹；仅看最终分数可能奖励错误路径，审计工具自身也可能误判。

这篇首次发表于 **2026 年 3 月**，在这里是评估方法的背景材料。它没有展示一个能长期改进自身改进机制的完整 RSI 系统，但可以帮助审查其他方法的“提升”有没有建立在固定任务与资源边界上。

## 自主性框架：任务内修正还不是持久自我改进

《The Last AI Built by Humans》按“改进责任有多少由系统承担”提出分析框架。最有用的起点是先看**变化是否保留下来，并影响未来独立任务**，而不是先给某个产品打等级。[原论文 v3](https://arxiv.org/pdf/2609.11873v3)

| 参照层级 | 系统承担的责任 | 需要寻找的证据 |
| --- | --- | --- |
| B0：任务内修正 | 改答案、调试或选择当前任务的候选结果 | 若没有持久系统变化，仍只是任务内改进 |
| L1：改进执行 | 按人给定的办法执行更新 | 具体更新产物及其采用条件 |
| L2：改进策略 | 在固定目标与评价下选择改进办法 | 策略选择、试验及保留记录 |
| L3：经验获取 | 决定下一轮需要什么学习经验 | 新经验如何补能力缺口并进入更新 |
| L4：环境适应 | 用部署反馈修订持久状态 | 后续任务是否继承更新，是否仍遵守外部采用规则 |
| L5：改进机制的递归继承 | 持久修改影响后续改进的机制 | 新的搜索、验证或后继生成机制是否进入下一轮 |

这是论文作者的分类框架，不是已经统一采纳的行业评级。会搜索文档、调用工具、反复调试，并不足以把 Copilot 或 Devin 直接定为 RSI 的某个高级别；必须知道具体系统保留了什么，以及它怎样影响下一轮改进。

## 更大尺度的反馈：AI 研发自动化

《What if automating AI R&D triggers an intelligence explosion?》讨论的是另一种尺度：更强的 AI 参与更多研发工作，研发产出又可能改善后继 AI，由此形成加速反馈。它不是一个新的 harness 算法，也不是已经复现的智能爆炸实验。[原报告 v2](https://arxiv.org/pdf/2609.36054v2)

该文首次发表于 **2026 年 9 月 28 日**，作者包括 Alan Chan、Christoph Winter、Geoffrey Hinton 和 Yoshua Bengio 等。实验室内部观测、经济模型推演和政策建议，应分别阅读；自动化代码贡献并不直接等于同等比例的研究能力增长，算力、实验周期、验证和组织协作仍可能构成瓶颈。

把它放在本专题，是为了连接“某个优化循环有效”与“整个研发过程是否加速”之间的问题。前面的系统论文不能单独证明这种宏观加速，这篇报告也不能替代对具体方法的控制实验。

## 三种收益不能直接排成一张榜

训练吞吐、被优化程序的加速比、Agent 的任务成功率，回答的是不同问题。即使都说“提升”，也不能把它们当成同一种能力。

| 阅读时要问 | 为什么影响结论 |
| --- | --- |
| 优化对象和正确性要求固定了吗？ | 改了任务本身，可能得到不可比的“收益” |
| 搜索、失败和验证花费算进去了没？ | 推理阶段更便宜，不代表完整优化过程更便宜 |
| 评估的是当前任务，还是没见过的任务？ | 任务内适应和跨任务泛化需要不同证据 |
| 谁判定可以采用新版本？ | 生成者自评、隐藏测试和独立复核提供不同保证 |
| 如何保存状态和回退？ | 代码能恢复，不代表外部动作也能撤销 |
| 权限与安全约束能被修改吗？ | 更会完成任务，不等于获得更广的授权 |

## 接下来值得跟踪什么？

我会优先跟踪三个问题：**验证成本是否随改进复杂度上升；经验能否迁移而不污染评测；长期改动是否仍遵守原来的权限与任务语义。** 这是跨工作阅读后的判断，不是这些论文共同证明的结论。

新的论文如果只在既有路线内换一个搜索器，适合放进日更；如果改变了反馈来源、状态管理或验证方法，就值得更新这个专题。后续阅读可以沿“固定任务 → 修改执行系统 → 协调模型与执行系统”展开，而不是把所有带 RSI 的标题放进同一类。
