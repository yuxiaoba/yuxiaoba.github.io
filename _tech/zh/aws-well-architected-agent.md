云优化常常停在发现列表：有的资源规格偏大，有的数据库缺少故障切换，有的配置偏离最佳实践。真正消耗团队时间的，是判断先改什么、改动会影响谁，以及怎样把建议转成可审阅的代码。AWS Well-Architected Agent 的预览把业务目标、资源与应用上下文、基础设施即代码（IaC）评审接到同一条建议链上。值得关注的是这条链如何形成，而不是把“Agent”理解为系统已能独立接管生产变更。

## 建议需要一个明确的优化对象

[服务概览](https://docs.aws.amazon.com/wellarchitected/latest/userguide/agent.html)描述了四类优化方向：成本、安全、韧性和性能。用户先定义 agent profile，再获得资源、应用或架构层面的建议。它继承已有优化服务的发现，并按业务目标安排优先级；公开材料没有展示一种新的底层推理算法，也没有给出修复成功率基准。

从工程上看，目标陈述本身就是输入质量的一部分。“降低费用”和“提高可靠性”会产生不同排序；一个不允许停机的核心系统，也不应与可重建的测试环境使用同一组约束。若目标没有写清，建议即使符合通用最佳实践，也可能不符合本地的维护窗口或恢复要求。

[概念文档](https://docs.aws.amazon.com/wellarchitected/latest/userguide/agent-concepts.html)把 profile 的账号与区域范围、业务目标以及应用上下文分开。应用信息可以补充重要性、架构描述和用于资源发现的标签。这里有一个关键设计取舍：自动发现能看到配置，却未必知道某个组件承载的业务含义，因此仍需要团队提供边界。

## 发现权限与变更权限分开理解

[入门指南](https://docs.aws.amazon.com/wellarchitected/latest/userguide/agent-getting-started.html)说明，执行角色负责组织扫描，并通过工作负载账号中的访问角色读取资源；自动创建的扫描角色是只读的。创建 profile 不等于授予 Agent 任意修改资源的能力。推荐中提供脚本或 IaC 改动，是把发现变成可执行候选，之后仍有部署决策。

权限缺失也会改变结果含义。某个应用没有发现记录，可能是访问角色、组织策略或采集范围的问题，不能直接解释为“没有风险”。这类系统需要把已覆盖、未覆盖和无法读取区分开；否则建议列表越短，看起来越健康，却可能只是看到的资源越少。

成本依据同样需要明确。指南说明，未启用 Cost Explorer 时会依据公开价格估算。对采用折扣或承诺用量的环境，建议中的成本变化与实际账单之间仍需核对。此处不是否定优化建议，而是明确决定其优先级的数据来自哪里。

## 在线资源与部署前模板，是两条路径

资源和应用建议按计划更新，服务概览给出的节奏是每周。架构评审则按需处理提交的 IaC 项目。[架构评审文档](https://docs.aws.amazon.com/wellarchitected/latest/userguide/agent-architecture-reviews.html)要求提供 S3 中的输入，选择评审支柱，并返回与原模板语言一致的修改建议；按需生成接口仅支持架构类型，不能据此触发资源与应用建议即时刷新。

这一区分决定了适用场景。周期扫描适合持续整理技术债与配置改进，不能充当秒级事故检测。模板评审可以在发布前暴露某些设计缺口，但只能依据提交内容理解系统，未必包含实际运行中的手工变更、外部依赖和负载行为。

一个工程上的假设例子是增加数据库副本：它可能改善某类故障下的可用性，同时增加费用，并引入复制或切换相关的应用条件。因此，评审不能停在“模板可以部署”。还需要核对应用连接方式、失败后的恢复步骤和可观察指标。这是对建议执行链的分析，不是 AWS 对某个真实系统的实测结果。

## 配额影响怎样安排评审

[配额文档](https://docs.aws.amazon.com/wellarchitected/latest/userguide/agent-quotas.html)列出的默认边界包括：单 profile 最多 100 个账号、10 个目标；架构评审每天最多 5 次；每次建议生成最多产出 30 条建议。后一个数字尤其说明，结果列表不应被理解为整个环境的完整问题清单。

输入也有容量限制：压缩包不超过 25 MB，S3 文件夹总量不超过 100 MB，文件夹内单文件不超过 1 MB。大型仓库需要考虑如何划分提交范围，同时保留跨模块依赖。拆得太细可能让评审看不见架构关系，打包过多又可能超过限制，不能简单把整个代码仓库当作无限上下文。

服务 profile 托管于美国东部北弗吉尼亚、俄亥俄或美国西部俄勒冈，可扫描商业区域资源。当前指南进一步限定使用资格为 Business+ 或更高支持计划；公告中宽泛的“有支持计划即可使用”不足以判断具体账号资格。应用级建议仍标为 beta，整体服务仍为 preview。

## 让候选变更进入已有发布流程

建议返回模板代码后，仍有一段必须保留的工程链：确定输入版本、审阅差异、验证依赖，再选择发布和回退方式。若实际环境已经偏离模板，直接应用看似正确的补丁可能覆盖未记录的配置。评审结果因此应绑定具体输入，不能成为对未来所有版本都有效的结论。

对应用级建议，还应寻找跨资源的反例。例如，一项节省实例成本的调整，可能把压力转移到数据库或网络；局部费用下降不等于系统总成本下降。验证时应观察建议目标及其邻近瓶颈，并在适当的业务周期内检查，而不是只看变更刚完成时的瞬时指标。

这条链也给可靠性评估提供了更具体的单位：建议被接受、成功部署、达到目标，以及没有引入相关退化，是四个不同阶段。把它们分别记录，才能判断 Agent 节省的是编写时间、部署时间，还是最终运维成本。

## 如何判断它是否有帮助

公开资料提供了流程和功能边界，尚未给出足以比较人工评审的准确率、遗漏率或长期成本收益。更合适的评估单位是一条建议：它依据哪些可见配置，为什么符合目标，修改影响哪些资源，是否需要跨组件验证，以及实施后用什么证据判断效果。

这次更新推进的是从发现到变更候选的连接。对系统可靠性团队来说，价值在于减少收集上下文、整理优先级和编写初稿的劳动，同时让最终变更仍能追溯到明确目标与证据。优先阅读扫描范围和架构评审两部分，再检查组织自己的变更流程能否接住这些候选，比仅看生成了多少条建议更有意义。
