Once LLM traffic shifts from isolated single-turn chat prompts into multi-step coding agents and reinforcement learning (RL) rollouts, serving performance ceases to be a property of a single engine's forward pass. Tool outputs append tens of thousands of repeated context tokens, bursts of sub-agent calls hit the cluster unevenly, and latency-tolerant background jobs compete for the same accelerators as interactive users. Co-founded by Google with Red Hat, IBM, and contributors from over 25 organizations (more than 500 contributors overall), CNCF Sandbox project **llm-d 1.0** connects PyTorch serving engines (`vLLM`, `SGLang`, `TorchTPU`) with Kubernetes control primitives (Gateway API Inference Extension, `LeaderWorkerSet`, Dynamic Resource Allocation) so admission control, cache locality, phase isolation, and multi-role rollouts operate as one coordinated cluster layer.

> **Source Lineage & Evidence Scope**: This reading note cross-checks the frozen Google Cloud 1.0 launch post alongside three frozen architectural/operational references, separating evidence into three tiers: **Tier 1** is the launch post itself (including the PyTorch Conference keynote demo with 1,000 sandboxed agents, three partner testimonials from Snap, ZenteiQ, and Mistral, and five linked benchmark/architecture posts); **Tier 2** comprises the shipped `v1.0` operational docs (`tiered-prefix-cache` and `llm-d-async`), which specify exact router sizing math, `/dev/shm` container-memory coupling, and two-level queue/pool gating; **Tier 3** covers the explicitly labeled **unreleased dev-version `DisaggregatedSet` documentation** (mirrored from `kubernetes-sigs/lws` KEP-766/846/848/849/960/1022) and the linked [`pd-disaggregation` guide](https://llm-d.ai/docs/well-lit-paths/foundations/pd-disaggregation)—whose rollout availability budgets and NIXL handshakes must be verified against the exact release deployed rather than treated as unconditional zero-downtime guarantees.

## Control Plane & Request Path: Envoy Inference Extension, EPP Scheduling, and Async Time-Slicing

Generic stateless load balancing—such as round-robin distribution behind a standard Kubernetes `Service`—fails multi-turn agent traffic in three coupled ways: replicas redundantly recompute identical prompt prefixes, accelerator HBM fills up with duplicated KV state, and bursty background loops stall interactive requests in shared queues.

On the routing plane, `llm-d` builds on the Kubernetes **Gateway API Inference Extension**, grouping model-serving pods behind an **`InferencePool`** resource and intercepting inference requests through **Envoy's External Processing (`ext_proc`)** gRPC hook. Whether running in **Gateway Mode** on managed [GKE Inference Gateway](https://cloud.google.com/kubernetes-engine/docs/concepts/about-gke-inference-gateway#llm-d-router) or in **Standalone Mode** with an Envoy sidecar proxy, the L7 data plane queries the **llm-d Endpoint Picker (EPP)** on every request. The EPP evaluates live prefix-index state, replica queue depth, and predicted latency, returning the chosen backend via the `x-gateway-destination-endpoint` header and `dynamic_metadata` so Envoy forwards directly to the warmest capable replica.

Around that core request path, `llm-d 1.0` integrates three scheduling extensions across heterogeneous fleets and background queues:

- **One endpoint across mixed TPUs and GPUs**: During the PyTorch Conference keynote, Google demonstrated 1,000 sandboxed agents on [Agent Substrate on GKE](https://cloud.google.com/blog/products/containers-kubernetes/bringing-you-agent-sandbox-on-gke-and-agent-substrate) hitting a single `llm-d` endpoint backed by `vLLM`, `SGLang`, and mixed Google Cloud TPUs and GPUs. With [TorchTPU](https://developers.googleblog.com/torchtpu-running-pytorch-natively-on-tpus-at-google-scale/), PyTorch models run natively inside upstream `vLLM` and `SGLang` without model rewrites; paired with `v1` APIs, session-aware routing, turn-priority scheduling, and native Responses API state, hardware additions or pool migrations remain infrastructure changes rather than agent rewrites.
- **BYOQ async admission with two-level gates and 6 strict lanes**: For latency-tolerant jobs whose SLOs span minutes or longer (bulk summarization, classification, offline workflows), [`llm-d-async-processor`](https://github.com/llm-d/llm-d-async) pulls messages from external queues (`redis-sortedset` recommended for production, `gcp-pubsub`, experimental Postgres `sql` with hash-partition leasing, and deprecated `redis-pubsub`). Admission separates **queue-level gates**—where `ActionRefuse` immediately returns the message to the broker for redelivery and frees the worker—from **pool-level gates** running inside the worker loop, where `ActionWait` **parks the worker in memory and polls** until capacity opens, avoiding broker nack/retry churn. Quota gates in `gating_mode: classifying` stamp requests as `reserved` or `overflow`, combining with queue `tier` labels (`interactive`, `async`, `batch`) to enforce **six strict priority lanes** (`0: reserved/interactive` down to `5: overflow/batch`) with per-`worker_pool_id` merge isolation so one saturated model pool never stalls another. Every message carries a mandatory Unix `deadline`, capping exponential-backoff retries and emitting `DEADLINE_EXCEEDED` on expiry.
- **Co-operative time-slicing for idle RL capacity**: During distributed RL post-training, accelerators often sit idle **40% to 60%** of the time waiting between rollout sampling and gradient updates. [`llm-d-rl-time-slicing`](https://github.com/llm-d-incubation/llm-d-rl-time-slicing) pairs lightweight `acquire()` and `yield()` client gRPC calls with an Accelerator Orchestrator and a node-scoped Snapshot Agent that checkpoints active CUDA state (~50 GB) into host DRAM in under a second, interleaving async inference into quiet intervals and lifting aggregate duty cycles from a **40% baseline to over 70%** without degrading RL convergence ([co-operative time-slicing blog](https://cloud.google.com/blog/products/containers-kubernetes/introducing-co-operative-time-slicing-for-rl-in-llm-d)).

Operationally, queuing and time-slicing require disciplined telemetry boundaries: time spent parked behind `ActionWait` or awaiting broker redelivery belongs in **end-to-end async job latency** rather than vanishing behind engine-only token-generation speeds, and multi-tenant evaluations must inspect low-priority completion rates and `DEADLINE_EXCEEDED` timeouts alongside high-priority tail TTFT.

## Tiered KV Offload & NIXL P/D Disaggregation: Memory Coupling, Cross-Pool Transfer, and Dual-View Reconciliation

When multi-turn sessions exceed local accelerator HBM, `llm-d` combines tiered KV offloading with disaggregated Prefill/Decode execution—each introducing strict sizing and protocol invariants documented in the frozen guides.

On the **tiered prefix-cache** side, the [v1.0 guide](https://llm-d.ai/docs/well-lit-paths/foundations/tiered-prefix-cache) supports three connector paths—`native` (recommended: vLLM `OffloadingConnector`, SGLang `HiCache`, and TorchTPU's `TPURaidenOffloadingConnector` / `tpu-sync`), `lmcache-connector`, and `mooncake-store` (embedded CPU DRAM under `cpu`, or a standalone Mooncake Client DaemonSet sized at **80 GB DRAM + 1 TB SSD** per node over `rdma/ib: 1` under `fs`). Four operational constraints in the guide govern whether offloading works as intended:

1. **Pod memory limits include `/dev/shm`**: vLLM allocates its host CPU tier inside `/dev/shm`, meaning offloaded KV blocks share the Pod's cgroup memory ceiling with weights and runtime RSS. For example, the TPU v7 single-host `Qwen/Qwen3.5-397B-A17B-FP8` overlay (`DP=8 × TP=1`, 262k context) pins 32 GiB host tier plus a 16 GiB `TPU_PREMAPPED_BUFFER_SIZE` staging buffer per engine (`850Gi` Pod request on `tpu7x-standard-4t` with ~919 GiB allocatable; doubling to 64 GiB per engine measured ~800 GiB RSS, leaving ~50 GiB headroom).
2. **Shared filesystems require deterministic hashing, `direct_io`, and external GC**: Under `VARIANT=fs` (`ReadWriteMany` PVC such as Google Cloud Managed Lustre, AWS EFS, or CephFS), TPU7x `TPURaidenOffloadingConnector` refuses to start without **`PYTHONHASHSEED=0`** because storage keys are prefix-block hashes that must match across pods so a fresh pod can restore a 22k-token prompt primed elsewhere. On parallel filesystems like Lustre, `raiden_storage_properties.direct_io` must stay `true` so KV reads bypass the Linux page cache and avoid competing with weights for host RAM. Crucially, **connectors never evict from the shared filesystem tier**—capacity reclamation requires storage-side limits or an external controller such as the reference PVC evictor in `llm-d-kv-cache`.
3. **Router-vs-engine split-brain hazard**: To steer follow-up turns toward pods holding evicted blocks in CPU RAM, the router runs two scorers (`gpu-prefix-cache-producer` and `cpu-prefix-cache-producer`). However, **vLLM does not report CPU-tier occupancy**—`vllm:kv_offload_cpu_cache_usage_perc` tracks only blocks pinned by *in-flight transfers*, not total fullness. Operators must manually set `lruCapacityPerServer = CPU tier bytes per pod / (64 × KV bytes per token)` (for `Qwen3-32B` at 256 KiB/token, 16 MiB per 64-token block gives `19200` for the 300 GiB NVIDIA default and `6400` for 100 GiB; TPU v7's 262k overlay switches to `4352`-token router blocks matching `--block-size`). Setting `lruCapacityPerServer` above actual `cpu_bytes_to_use` causes the router to chase prefixes that the engine already evicted. While SGLang `HiCache` exports actual occupancy (`sglang:hicache_host_used_tokens / hicache_host_total_tokens`), the guide also warns that **bundled alerting rules do not cover offloading yet**.
4. **Asymmetric NIXL protocols in P/D disaggregation**: When splitting compute-bound `Prefill` from bandwidth-bound `Decode` (plus optional multimodal `Encode`), **NIXL** moves KV state over RDMA (InfiniBand/RoCE/EFA, or TCP fallback). Per the linked [`pd-disaggregation` guide](https://llm-d.ai/docs/well-lit-paths/foundations/pd-disaggregation), engine semantics diverge sharply: **vLLM (`NixlConnector`) uses a pull model**, where Decode workers read KV blocks directly out of Prefill GPU memory via one-sided RDMA P2P reads and retain fallback capability under matching parameters; **SGLang uses a push model**, coordinating via a Prefill bootstrap server (port `8998`) and NIXL side-channel handshake (port `5600`) so Prefill actively pushes KV blocks—and `--disaggregation-mode=decode` **has no local-prefill fallback**, rejecting any request missing the `bootstrap_host`, `bootstrap_port`, and `bootstrap_room` fields injected by the Routing Proxy Sidecar and EPP.

From an engineering trade-off perspective (derived from the documented mechanisms rather than benchmarked across every permutation), both capabilities obey strict **break-even inequalities**: CPU or Lustre offloading reduces TTFT only when index lookup, queue delay, and PCIe/storage restore latency remain smaller than recomputing the prefix; similarly, P/D disaggregation pays off only when eliminating prefill-decode interference outweighs cross-node NIXL transfer latency and operational complexity.

## Cross-Role Zero-Downtime Upgrades: DisaggregatedSet Coordination Budgets, Slices, and Revision Gating

Splitting Prefill, Decode, and Encode into independent pools with distinct container images, tensor-parallel widths, or accelerator types turns rolling updates into a cross-role coordination problem. In the [`DisaggregatedSet` design documentation](https://llm-d.ai/docs/dev/architecture/model-server-orchestration/disaggregatedset) (**again noting that this document is explicitly marked as `dev`-version unreleased documentation mirrored from `kubernetes-sigs/lws`**), the architecture prevents "locally ready Pods, globally broken path" outages through four controls:

- **Parent-child orchestration and topology isolation**: `DisaggregatedSet` does not replace `LeaderWorkerSet` (LWS); it composes one child LWS per role (`<ds>-<slice>-<rev>-<role>`), requiring label selectors rather than hardcoded resource names because revision hashes rotate on update. `spec.slices` replicates entire P/D/E topologies as independent fault domains, while `spec.placementPolicy` enforces scheduling constraints: `ExclusiveSlice` co-locates all roles within a slice inside one topology key (e.g., `topology.kubernetes.io/rack` or `cloud.google.com/gke-placement-group`) for low-latency NIXL transfers while spreading slices across domains; `ExclusiveTopology` injects Pod anti-affinity for 1:1 domain-to-slice exclusivity across all `DisaggregatedSet`s (though non-`DisaggregatedSet` cluster workloads can still land in the domain unless node taints isolate it).
- **Singleton outage trap and fractional coordination windows**: Child roles default to `maxSurge: 0, maxUnavailable: 1` (like LWS), yielding a Ready floor of `max(0, replicas - maxUnavailable)`. On a singleton role (`replicas: 1`), `maxUnavailable: 1` permits **100% unavailability**, taking down the entire serving path even while peer Decode pods remain healthy; keeping singleton roles continuously live demands `maxUnavailable: 0`, positive `maxSurge`, and spare accelerator capacity. Because role sizes differ (e.g., updating `4 Encode, 13 Prefill, 7 Decode` groups), the controller coordinates retirement and creation proportionally using a **fractional coordination window** of width `1 / smallest non-zero role count` (`1/4 = 25%` in that example). Meanwhile, `spec.scalingPolicy.scaleDownDuringRollout` separates `Deferred` (default, holding created target replicas until old drains) from `Immediate` (reclaiming excess old replicas or unscheduled target replicas sooner while still honoring `effective desired - maxUnavailable` Ready groups—never instant deletion when deleting Ready groups could breach availability floors).
- **Stable autoscaling targets and virtual sub-roles**: Because child LWS names embed changing revision hashes, pointing HPA or KEDA directly at an LWS breaks across upgrades. `DisaggregatedSetRoleScaler` (KEP-849) maintains a constant `<ds>-<role>` `/scale` target per role (currently restricted to `spec.slices: 1`). Where a single shared-template LWS needs differentiated routing pools (such as `subRoles: [{name: interactive, replicas: 3}, {name: batch, replicas: 1}]`, KEP-960), pods carry `disaggregatedset.x-k8s.io/subrole` and Hash scale-down hints `PodDeletionCost`—though Kubernetes ReplicaSet still prioritizes keeping scheduled, healthy leaders over subrole cost preferences on a best-effort basis.
- **Revision gating (`rollout-screener` + Coordinator)**: Old Revision A and new Revision B may use incompatible KV-cache layouts or transfer protocols, making cross-revision Prefill-to-Decode handoffs unsafe. Configuring `disaggregatedset-rollout-screener` (`mode: max-role`, `requiredRoles: [prefill, decode]`) inside `EndpointPickerConfig` blocks *all* traffic to Revision B until **at least one Pod is Ready in every required role**. Traffic across eligible revisions is then weighted by Ready **Pods** in the largest role (e.g., 6 Ready Decode pods in A and 4 in B sends 40% to B—counting Pod heads rather than GPUs or measured throughput). When running separate Prefill and Decode routers, the Prefill router picks the revision and the **llm-d coordinator** forwards the `x-llm-d-disagg-revision` header so Decode stays pinned to the exact same revision.

To keep evaluations reproducible rather than anecdotal, `llm-d` ships the open-source [**Prism**](https://prism.llm-d.ai/) benchmark explorer backed by standardized [`llm-d-benchmark`](https://github.com/llm-d/llm-d-benchmark) recipes and [`inference-perf`](https://github.com/kubernetes-sigs/inference-perf) multi-turn workloads—letting operators inspect exact published configurations or upload internal runs to compare throughput, latency, and cost curves under identical traffic.

Synthesizing the blog's four-step *Get started* progression with the operational safeguards across our three frozen primary docs yields a disciplined rollout ladder where every layer earns its complexity under controlled measurement:

1. **Start with prefix-aware routing (EPP) and preserve real inter-turn gaps**: Place the `llm-d` router in front of existing `vLLM` or `SGLang` pods and replay realistic agent trajectories—preserving the tens of seconds spent executing external tools rather than collapsing turns back-to-back—to measure actual `vllm:prefix_cache_hits_total` and TTFT gains before adding storage complexity.
2. **Add priority flow control and async admission boundaries**: When batch loops share accelerators with interactive traffic, enforce priority bands or deploy `llm-d-async-processor` with `reserved`/`overflow` lanes and isolated `worker_pool_id` channels, counting `ActionWait` and broker redelivery latency inside end-to-end job completion times while monitoring `DEADLINE_EXCEEDED` rates.
3. **Enable tiered KV offload with strict router-engine reconciliation**: Introduce `OffloadingConnector` / `HiCache` / `TPURaidenOffloadingConnector` only when HBM eviction drives measurable recomputation. Budget `/dev/shm` and staging buffers inside Pod memory limits, calibrate `lruCapacityPerServer` to match `cpu_bytes_to_use`, enforce `PYTHONHASHSEED=0`, `direct_io=true`, and an external PVC evictor on `VARIANT=fs`, and continuously cross-check `llm_d_epp_prefix_indexer_hit_ratio` against `vllm:external_prefix_cache_hits_total`, `kv_offload_store/load_bytes_total`, `load_time_total`, and `kv_offload_allocation_failure_total` so a write-only or slow-restore tier is caught immediately.
