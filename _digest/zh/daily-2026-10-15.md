本期最值得先读的是 ReFlow 与 CQ2-CARE：前者把昂贵的生成轨迹重复用起来，同时控制策略过时与 GPU 分工；后者把编码上下文的目标从“压缩得更短”推进到“找对文件，并保留能精确编辑的代码”。两项工作都提醒我们，省下计算或 token 以后，还要检查学习进展和任务完成率是否保住。

推理服务方面，三篇 KV 存储研究分别追查逐对象开销、SSD 部分块放大和远端服务排队，说明命中率本身不足以判断收益。可靠性方面，ExecWeave 区分观察与推断，Diviner 将知识更新交给回放和人工审核，MCP-FSD 检查工具意图与实际权限的落差。它们提供的是不同层次的机制与证据，适合按自身关注的训练、服务或诊断环节继续阅读。

<h2 class="daily-paper-title" id="paper-arxiv-2610.21640">01 · ReFlow：让近期轨迹多次参与训练，同时控制过时程度</h2>

[ReFlow: Replay-Driven Decoupling for Efficient RL Post-Training](https://arxiv.org/abs/2610.21640v1)  
Yukun Tian 等 · 2026-10-15 · Chuan Wu 参与

强化学习后训练的等待，常发生在生成和更新之间：模型需要逐 token 生成轨迹，工具调用又引入不同长度的停顿；训练器即使已经空闲，也可能凑不齐下一批数据。异步执行能把两阶段重叠，但进一步放宽策略版本差距，可能让数据与当前模型越来越不匹配。ReFlow 的选择是复用近期已经消费过的轨迹，减少每次更新所需的新生成量，并随之调整 GPU 分工。**它改变的是训练数据的生命周期，以及生产数据和消费数据的速度关系。**

### 复用多少，与旧数据影响多大，分开控制

输入提示先进入流式生成队列，完成的轨迹逐条写入缓冲区。训练器从未使用数据与回放数据中组批，不必等整批生成结束。回放比例可以随供需变化，但受上限约束；系统另外降低回放样本在损失中的相对权重，并限制允许使用的策略版本差距。于是，“一半样本来自回放”并不等于“一半更新影响来自旧数据”。

<a class="note-image-link" href="/assets/images/digest/2026-10-15/reflow.png" target="_blank" rel="noopener" aria-label="ReFlow：让近期轨迹多次参与训练，同时控制过时程度 · 查看原图 ↗"><img src="/assets/images/digest/2026-10-15/reflow.png" alt="ReFlow：让近期轨迹多次参与训练，同时控制过时程度" loading="lazy"><span class="note-image-action">查看原图 ↗</span></a>

*左上持续生成，右上缓冲区控制样本年龄与回放；下方训练器消费数据，中间调度器同时调节资源和参数同步。*

论文实验把回放比例上限和相对损失权重都设为 0.5，允许最新及前一版本的数据。其简化分析在等权 token 量等假设下，说明此时回放的梯度混合权重最多为三分之一；这是局部误差分析，不是任意任务上的收敛保证。作者也展示了直接按固定比例回放会拖慢学习的例子，因此不能只取“重复用数据”而省掉稳定性控制。

### 数据节省以后，机器也要重新分工

回放降低了生成需求，原有固定 GPU 划分可能反而浪费资源。ReFlow 的统一 worker 预先准备训练与推理能力，将暂时不用的模块卸载到 CPU；重分配时按完整副本组切换角色，尽量保留已有分片，并给新训练副本传输对应分片。调度器根据实际生产、消费与空闲比例调整分工，同时参考 KV 占用和抢占压力调节生成并发。这样既避免每次扩缩都冷启动，也避免把更多请求简单塞进已拥堵的生成端。

### 吞吐收益需要和奖励进展一起看

作者在最多 128 张 H800 上测试 Qwen3-4B 至 32B，以 VeRL、one-step-off 和 VeRL-async 为基线。单轮 DAPO-Math-17K 的训练吞吐提升为 1.19–2.06×；APPS 多轮编码任务为 1.07–1.92×；ReTool 的 Qwen3-8B 配置在 16/32 张 GPU 上为 1.31–1.82×。吞吐按训练器每步处理的 token 数除以步时长计算，包含被复用的数据，不能解释为新生成样本增加同样倍数。

训练奖励曲线显示，在这些设置中，系统能更早达到相近奖励。32 张 GPU 的角色调整仍需 5.72 或 9.20 秒，并非无成本。**优先读数据循环与资源重分配两部分：**它们把算法允许的样本复用转化为系统调度空间。长期泛化、不同奖励机制和更长训练过程仍需更多证据；论文的奖励轨迹也不能替代独立下游测试。

<h2 class="daily-paper-title" id="paper-arxiv-2610.21073">02 · CQ2-CARE：先选对待修改文件，再保留可精确编辑的原文</h2>

[Skip the Compressor: Coding Agents Fix More Issues When They Pick Whole Files](https://arxiv.org/abs/2610.21073v1)  
Xiaocong Yang、Rishit Chatterjee、Himanshu Udupi、Vikram Ramavarapu、ChengXiang Zhai · 2026-10-15

编码 Agent 面对大仓库时，通常需要检索代码片段或压缩上下文。问题在于，修复 issue 同时需要两种信息：应该修改哪个文件，以及该文件原来究竟怎样写。语义相似度可能把预算花在同名测试、文档或调用者上；逐 token 压缩则可能保住了文件名，却改坏补丁必须引用的源代码。CQ2-CARE 把预算优先用于少量完整文件，让“定位”和“可编辑性”共同成为评价目标。

### 从路径清单到完整文件

模型先看 issue 和筛选后的路径清单，独立给出待修改文件的排名；选择两次回答共同指出的非测试、非文档路径，交集为空时回退到另一份排名。随后，模型提出最多四项定向搜索，补充定义或调用者等证据，最多来自八个其他文件。最终上下文由选中文件和证据片段组成，仍有单块与总量上限，并非无限制装入仓库。

<a class="note-image-link" href="/assets/images/digest/2026-10-15/whole-files.png" target="_blank" rel="noopener" aria-label="CQ2-CARE：先选对待修改文件，再保留可精确编辑的原文 · 查看原图 ↗"><img src="/assets/images/digest/2026-10-15/whole-files.png" alt="CQ2-CARE：先选对待修改文件，再保留可精确编辑的原文" loading="lazy"><span class="note-image-action">查看原图 ↗</span></a>

*从上到下比较检索、token 裁剪和整文件选择：前者可能找错文件，中间可能破坏引用文本，下方保留可定位的源代码；右侧是总体解决率。*

实验不是先规定统一的 16K 或 32K 窗口，而是先生成每个 issue 的 CQ2-CARE 上下文，再把其实际 token 数作为该题所有方法的目标预算。这个设计适合回答“在选择器使用的预算下怎样组织上下文”，对任意固定窗口的结论则要看额外预算扫描。模型只生成一次补丁，由测试判断是否修复；不能直接把结果当作可反复读文件、运行测试的多轮 Agent 排名。

### 两种失败如何分开观察

作者使用 SWE-rebench 中 300 个 Python issue，每个来自不同仓库，并先确认正确补丁能通过、空补丁不能通过。GPT-5.6 与 Claude Opus 5 的解决率分别为 43.7% 和 46.7%，相对各自最佳压缩基线均高约 6.3 个百分点，相对最佳普通检索基线高 9.3 和 12.7 个百分点。训练过的函数检索器 SweRank 则只落后 0.7 和 1.7 个百分点，显示“选取合适且保持原样的代码”可以有不同实现。

诊断实验更有解释力：固定所选文件、删去每行 20% token，GPT-5.6 的补丁可应用率从 98.0% 降至 78.7%，解决率降低 9.7 个百分点。但当 LongCodeZip 使用 CQ2-CARE 的同一候选文件集合时，解决率达到 44.7%，与 43.7% 接近。**证据支持先把文件选对、保持代码行完整，而不是所有压缩必然无效。**

### 对上下文工程的启发

两次定位回答的一致性提高了文件级 F1，但把单次回答截到相同文件数量也能取得接近结果；收益主要来自克制地选择少量文件，不能把一致性机制单独神化。GPT-5.6 下，作者估计完整流水线 API 成本为每题 0.151 美元，压缩方案仅 API 部分为 0.168–0.177 美元，后者还需压缩模型计算。

这篇值得优先读控制实验与讨论：它把“上下文更短”转成“补丁能否落到真实代码”的可检验问题。边界是单轮、Python、一个基准及大多数格子仅一次补丁采样；小幅差距尤其容易受采样和潜在训练数据重合影响。多轮系统能否通过重读弥补压缩损失，还需把额外轮次和 token 成本一起衡量。

<h2 class="daily-paper-title" id="paper-arxiv-2610.21146">03 · ExecWeave：把执行关联的证据强度也画进图里</h2>

[ExecWeave: Cross-Layer Execution Provenance for Observable Agentic Software](https://arxiv.org/abs/2610.21146v1)  
Guo-Wei Wong、Meng Chang Chen · 2026-10-15

Agent 的工具记录与操作系统事件并不天然共享身份。ExecWeave 分别采集框架语义、模型网关和进程／文件／网络事件，构建带来源、推断与因果状态的执行图。命令到进程的启发式连接只在观察到唯一兼容候选时生成；候选不止一个就拒绝归因。

<a class="note-image-link" href="/assets/images/digest/2026-10-15/execweave.png" target="_blank" rel="noopener" aria-label="ExecWeave：把执行关联的证据强度也画进图里 · 查看原图 ↗"><img src="/assets/images/digest/2026-10-15/execweave.png" alt="ExecWeave：把执行关联的证据强度也画进图里" loading="lazy"><span class="note-image-action">查看原图 ↗</span></a>

*三路证据先各自保留，再标准化成图；虚线分支表示可选的推断连接，不能当成直接观察到的因果关系。*

关键负对照表明，真实进程漏采而只剩一个冒名候选时，“唯一”仍会连错。Linux 可移植采集器在 20 ms 轮询下，对实际约 16 ms 的短进程仅检出 18/30 次；固定工作量实验的时间开销中位数为 62.3%–408.8%。因此它更值得作为**显式表达不确定性的可观测性设计**阅读，而非完整、低开销的因果追踪保证。AutoGen–Ollama 的单例验证也不代表跨框架覆盖。

<h2 class="daily-paper-title" id="paper-arxiv-2610.21241">04 · Range：缓存切得更细，不再逐对象付存储开销</h2>

[Range: Decoupling KV-Cache Reuse Granularity from Storage Work](https://arxiv.org/abs/2610.21241v1)  
Dingsen Shi 等 · 2026-10-15

同样恢复 6 GiB KV，逻辑对象从 192 个增到 6,144 个，查询、分配与搬运次数也可能一起增长。Range 用范围票据表达可复用前缀，以固定字节条带组织物理 I/O，再由传输缓冲区跟踪异步完成；每层数据就绪后才放行该层注意力，使复用粒度与存储批次脱钩。

<a class="note-image-link" href="/assets/images/digest/2026-10-15/range.png" target="_blank" rel="noopener" aria-label="Range：缓存切得更细，不再逐对象付存储开销 · 查看原图 ↗"><img src="/assets/images/digest/2026-10-15/range.png" alt="Range：缓存切得更细，不再逐对象付存储开销" loading="lazy"><span class="note-image-action">查看原图 ↗</span></a>

*左侧票据确定复用范围，右侧缓冲区读入并散射到 KV 槽位；每层完成后才开始注意力，下方写回等全部层完成才发布。*

在单张 H100 NVL、Llama-3.1-8B-Instruct、BF16 KV、65,280-token 请求且缓存 49,152 token 的设置中，作者测得 Range 的 TTFT 为 1.788–1.803 秒；调优后的进程内 cuFile 路径在普通粒度扫描中从 2.124 增至 3.012 秒。**值得看整条路径如何维持批处理单位**，而非只看 SSD 带宽。每格仅三次、逐请求运行，多 rank 已实现但未测；并发服务与碎片化前缀仍是外推边界。

<h2 class="daily-paper-title" id="paper-arxiv-2610.21249">05 · LMCache SSD 实证：命中更稳定，也可能更慢</h2>

[Characterizing Predictability-Latency Trade-offs of KV-Cache SSD Offloading in LMCache for LLM Serving Systems](https://arxiv.org/abs/2610.21249v1)  
Ying He 等 · 2026-10-15

这项研究比较两套可运行部署：LMCache 0.3.0 的缓冲 I/O，与 0.3.16.dev11 的前缀去重加 O_DIRECT。四类短上下文各发 100 个无状态请求。完全重复输入的写入从 1.62 GB 降到 11.75 MB，但后续 99 次请求每次仍读约 12 MB，平均 warm TTFT 从归档记录的 27 ms 增至 93.1 ms。

<a class="note-image-link" href="/assets/images/digest/2026-10-15/ssd-offload.png" target="_blank" rel="noopener" aria-label="LMCache SSD 实证：命中更稳定，也可能更慢 · 查看原图 ↗"><img src="/assets/images/digest/2026-10-15/ssd-offload.png" alt="LMCache SSD 实证：命中更稳定，也可能更慢" loading="lazy"><span class="note-image-action">查看原图 ↗</span></a>

*首个冷请求后，重复请求的延迟集中在较窄区间；稳定的 warm 路径仍有每次读 SSD 的成本。*

原因是约 94-token 输入在 GPU 上已命中 80 token，剩余 14 token 却触发整个部分块读取；旧栈的低读取量则依赖操作系统页缓存。**这为“命中后读回还是重算”提供了块设备证据。**版本、SSD 与 I/O 模式同时变化，不能把差异全归因于单个开关；不足两个 256-token 块的输入也不能代表长前缀 RAG。原文没有整体架构图，这里用请求延迟图展示其研究对象。

<h2 class="daily-paper-title" id="paper-arxiv-2610.21281">06 · Diviner：诊断经验进入可回放、有人审核的改进循环</h2>

[Diviner: Agentic RCA with Human-Governed Adaptation for Large-Scale Infrastructure](https://arxiv.org/abs/2610.21281v1)  
Pradipta Ghosh 等 · 2026-10-15

Meta 的 Diviner 把事故知识编码成技能、工作流和历史知识图，由 Lead–worker 协作查询实时证据；历史相似事故只产生假设，不能直接证明当前根因。保存的轨迹交给 DivinerEval 找出知识或工具缺口，修改须通过回放及负责人批准；系统提供建议，不自动执行缓解操作。

<a class="note-image-link" href="/assets/images/digest/2026-10-15/diviner.png" target="_blank" rel="noopener" aria-label="Diviner：诊断经验进入可回放、有人审核的改进循环 · 查看原图 ↗"><img src="/assets/images/digest/2026-10-15/diviner.png" alt="Diviner：诊断经验进入可回放、有人审核的改进循环" loading="lazy"><span class="note-image-action">查看原图 ↗</span></a>

*从上方经验编码进入中间实时调查，再沿下方评估与审批回到知识库；人工批准位于更新重新进入系统之前。*

同模型对照中，Diviner + Claude 相对普通 Claude 的 Exact RCA 高 11 个百分点（95% CI：3–20），平均耗时低 52%（44–58）。运营观察队列中约 52% 的缓解时间下降是另一项关联结果，受事故构成、人员与采用方式影响。**值得读的是知识治理和证据契约。**整套 harness 的收益不能归给某一个模块，工具未返回数据也不能被当作“该原因不存在”。

<h2 class="daily-paper-title" id="paper-arxiv-2610.21463">07 · SpecAgent：小模型先探索，大模型在写操作前审核</h2>

[Trajectory-Level Speculation with Semantic Verification for Tool-Using Agents](https://arxiv.org/abs/2610.21463v1)  
Zilin Wang、Yinhong Liu、Chao Chen、Qun Liu、Zhijiang Guo · 2026-10-15

SpecAgent 让小模型执行读取类工具并积累真实观察，遇到改变状态的动作先暂停。大模型一次读入整段轨迹，保留语义有效的前缀，并尽量在判定中直接给出修正动作，降低逐步生成的成本。

<a class="note-image-link" href="/assets/images/digest/2026-10-15/specagent.png" target="_blank" rel="noopener" aria-label="SpecAgent：小模型先探索，大模型在写操作前审核 · 查看原图 ↗"><img src="/assets/images/digest/2026-10-15/specagent.png" alt="SpecAgent：小模型先探索，大模型在写操作前审核" loading="lazy"><span class="note-image-action">查看原图 ↗</span></a>

*上方强模型逐步生成；下方小模型先执行读取，写动作暂存，由强模型接受有效前缀并修正后继续。*

<h2 class="daily-paper-title" id="paper-arxiv-2610.21500">08 · 远端 KV：把存储并行度跟上上下文并行</h2>

### RaReCache：跨模型复用 KV，按秩分歧选择重算位置

[RaReCache: Bridging the Gap in Cross-Model KV Cache Reuse via Rank disagreement-based Selective Recomputation](https://arxiv.org/abs/2610.11358)  
Sreetama Sarkar、Saptarshi Mitra、Sitao Huang、Souvik Kundu、Peter A. Beerel · 论文：2026-10-08 · [Sasha Malysheva 原帖](https://x.com/aimalysheva/status/2110760611026206814)：2026-10-15

RaReCache 先用离线拟合的线性映射转换小模型 KV，再比较完整映射与降秩映射，挑选落在校准数据支持较弱方向上的 token，让目标模型只重算这些位置。Qwen3-0.6B→14B 在完整 GSM8K 测试集上，重算 30% 位置将准确率从纯映射的 71.6% 提高到 90.2%，目标模型独立运行是 95.1%。

*源 KV 同时经过完整映射与降秩映射，差异决定重算位置；右侧目标缓存混合映射状态和重算状态。*

最高 3.04× prefill 加速来自 A100 80GB、平均 149-token 输入、批处理、20% 重算，且假定源 KV 已存在；不是上述 30% 精度配置，也不包含首次小模型 prefill。低负载时，框架调度开销还可能使它更慢。**优先看选择指标为何优于注意力权重，以及精度与服务负载怎样共同决定收益。**已验证配对使用同家族共享 tokenizer 的模型，不能理解为任意模型间无损转换。
