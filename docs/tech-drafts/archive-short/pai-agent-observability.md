**Partnership on AI · 可观测性评估报告**  
原文：The Observability Gap in AI Agents · [报告 PDF](https://partnershiponai.org/wp-content/uploads/2026/10/PAI_obervability-gap-in-ai-agents.pdf)

## 有调用链，还缺什么

一条 trace 可以显示 Agent 读取了文件，却未必能说明它当时以什么身份、在什么权限下读取。如果会话中途放宽了审批模式，或者子 Agent 继承了不同的权限，事后只看工具调用成功，可能无法重建授权过程。

PAI 的报告把问题放在监控工具之前：**框架是否发出了回答这些问题所必需的记录？** 下游分析平台即使能够关联和展示事件，也通常无法补回从未被记录的状态变化。

## 从目标倒推数据，而不是从已有日志猜用途

![PAI 的监控目标、处理技术与遥测缺口分析框架](figures/pai-framework.png)

*读图：从上往下看“要监控什么 → 如何形成信号 → 缺少什么记录 → 谁能补齐”。这是报告的分析框架，不是一套已经部署的产品架构。*

报告先提出六类目标，包括识别越权、策略违反、人工监督失效、行为漂移、多 Agent 风险及支持事后审计，再分析所需的数据处理方式。例如，判断越权需要把行为关联到有效身份与权限；发现漂移需要跨运行建立基线；追踪委托关系需要连起多个 Agent 的事件。

这个顺序很实用：先明确“我们要识别哪一种失败”，再检查字段与关联是否充分。它避免了把日志数量或 dashboard 完整程度当成监控能力。

## 具体缺口在哪里

报告评估了 OpenAI Agents SDK、Claude Agent SDK、LangGraph 和 CrewAI 的技术文档。其结论首先应理解为**该次文档评估的时点快照**，并非对所有部署配置的实时测试。

其中四类缺口与执行记录直接相关：

| 记录 | 希望回答的问题 |
| --- | --- |
| 持久 Agent 身份 | 跨会话、跨子 Agent 后，能否确认是谁在行动？ |
| 权限模式变更 | 何时、由谁把审批或自主执行模式改了？ |
| 记忆变更 | 哪次写入改变了后续行为，写入因何发生？ |
| 人工介入 | 为何升级、谁审核、具有何种权限、做了什么决定？ |

另外两类是推理过程和 token 级概率。它们更多依赖模型提供方是否暴露相关信息，而且信号的解释本身仍有不确定性。报告并不认为拿到推理文本就等于知道了真实决策原因，也不把 token 概率视为可靠的任务正确性分数。

因此，两类问题的工程路径不同：明确的执行事件可以通过补充字段、标准和采集实现改善；关于决策过程的信号，还需要研究其有效性。

## 这份评估有多强的证据

作者从两个假想金融业务场景出发，通过工作组讨论整理监控目标，然后逐字段评审四个框架的文档，采用 AI 初筛再人工核对。它提供了可检查的字段清单和分析依据，但没有通过大规模生产流量或故障注入测量这些缺口实际造成了多少失败。

这也决定了适合怎样使用它：可以用来审视自己缺少哪些记录，不能拿框架间的色块评分直接判断哪一个产品最安全。框架版本、额外插桩和组织自己的身份系统，都可能改变实际可观测性。

## 工程判断：把它作为监控需求的检查表

落地时可以挑一个最关心的风险，沿图中的依赖链检查。例如，若要发现审批被绕过，应同时找到动作记录、当时的权限状态、模式变更事件和审核者身份；仅有“工具执行成功”并不够。

这份报告的价值是把“需要更好的 observability”落实为具体数据要求。对已经在做轨迹评分或根因分析的系统，先确认输入证据是否完整，往往比再增加一个分析面板更关键。报告没有提供可直接部署的诊断系统，技术文档结论也应在采用时按所用版本重新核对。
